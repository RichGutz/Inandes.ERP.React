## 📋 Vistas del Módulo

### 1. Pestaña "Datos del Inversionista"
- Tabla enriquecida con búsqueda en tiempo real por DNI, RUC o Nombre.
- Desglose de Cuentas Bancarias registradas (Banco, N° Cuenta, CCI) para PEN y USD.
- Estado de cumplimiento / compliance (Aprobado, Pendiente, Rechazado).
- Exportación directa a Excel mediante SheetJS (`XLSX.writeFile`).

### 2. Pestaña "Auditoría de Retornos"
- Proyección y devengue mensual de retornos por contrato.
- Aplicación de retención fiscal del 5% de Impuesto a la Renta de 2da Categoría sobre los intereses generados.
- Resumen consolidado del Portafolio AUM (Asset Under Management) por moneda.

### 3. Pestaña "Documentos y Expediente" (Tab C)
- Carga, previsualización y generación masiva de **Estados de Cuenta (EECC)** y **Certificados de Retención de Renta (2da Cat)**.
- Canales integrados de notificación: **Email Institucional (SMTP)** y **WhatsApp (Evolution API)** con pausas anti-saturación.
- Parámetros de Cierre Fiscal: `Fecha de Operación` y `Tipo de Cambio (TC USD/PEN)`.

## 🏛️ 4. Persistencia Inmutable de Fecha de Operación y Tipo de Cambio (TC) en el Ledger

### 🎯 El Problema Técnico y Tributario
Al liquidar fondos en **Dólares (USD)**, la retención del **5% de Impuesto a la Renta de Segunda Categoría** debe convertirse y declararse a **SUNAT en Soles (PEN)** aplicando el Tipo de Cambio (TC) oficial del día en que se ejecuta la operación bancaria y se pagan los rendimientos (`Fecha de Operación`).

Si el TC y la Fecha de Operación solo se ingresan como variables temporales en la UI al momento del envío masivo:
1. **Volatilidad:** El TC del día no queda guardado de forma permanente en la fila contable del evento.
2. **Discrepancia en Consultas a Pedido (Bot de WhatsApp):** Si semanas o meses después un inversionista solicita sus EECC o Certificados de Retención históricos por WhatsApp, el bot no sabría con qué TC exacto se declaró ante SUNAT ese pago, arriesgando incongruencias fiscales.

### 💡 La Solución Arquitectónica (Control Explícito del Administrador)

Para evitar que envíos parciales o pruebas sobreescriban accidentalmente los datos oficiales de todo el fondo, se implementa un **control deliberado y explícito**:

1. **Checkbox en UI (Tab C):**  
   Al costado derecho del campo `TC`, se incorpora el checkbox:  
   $$\boxed{\checkmark}\ \textbf{Registrar Fecha de Operación y TC en Ledger}$$
2. **Persistencia en Supabase (`crm_certificados_eventos`):**  
   Cuando el administrador marca el checkbox y despacha/formaliza los reportes, el sistema congela en el campo `payload_asiento` (JSONB) y en `fecha_pago_real` los valores exactos:
   ```json
   {
     "tipo_cambio": 3.7500,
     "fecha_operacion": "2026-09-10",
     "fecha_pago_real": "2026-09-10",
     "registrado_por": "operaciones_admin",
     "registrado_el": "2026-09-11T17:30:00Z"
   }
   ```
3. **Consumo Determinista por el Bot de WhatsApp:**  
   El Bot de WhatsApp lee prioritariamente `payload_asiento.tipo_cambio` y `payload_asiento.fecha_operacion` de cada evento. Si existen, genera el PDF histórico **con el TC oficial inmutable de la fecha de pago**, garantizando 100% de coherencia con SUNAT y contabilidad.

## 🌾 5. Plan de Seeding y Estandarización de Eventos Históricos (< 31-AGO-2026)

### 🎯 Diagnóstico de la Brecha Histórica
Todos los eventos contables cerrados en `crm_certificados_eventos` con fecha anterior al 31 de agosto de 2026 (cortes de `2026-02-28`, `2026-04-30`, `2026-06-30`, etc.) fueron liquidados y formalizados antes de la implementación del motor de persistencia inmutable en `payload_asiento`.

Actualmente, estos registros presentan:
* `payload_asiento: null` o sin claves `tipo_cambio` / `fecha_operacion`.
* `fecha_pago_real: null` en algunos eventos.

### 💡 Justificación: ¿Por qué es Indispensable el Seeding?
1. **Estandarización y Paridad de Esquema (Schema Parity):** El 100% de los registros en el Ledger deben responder al mismo contrato de datos, eliminando la deuda técnica de tener "eventos antiguos" sin campos fiscales.
2. **Garantía Absoluta para el Bot de WhatsApp:** Cuando cualquier inversionista solicite a demanda su Certificado de Retención de bimestres anteriores (ej. Mayo-Junio 2026), el bot encontrará inmediatamente el TC oficial con el que se declaró ante SUNAT dicho periodo, sin requerir condicionales complejos ni adivinaciones en caliente.
3. **Trazabilidad Contable / Auditoría APEFAC:** Asegura que los reportes PDF generados desde el ERP coincidan al milímetro con los descargados por los clientes desde sus dispositivos móviles.

### 🛠️ Mecánica de Ejecución del Seeding

El procedimiento se ejecutará mediante un script idempotente en Python (`scratch/seed_historical_events_tc_fop.py`) siguiendo estas reglas estrictas:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      MATRIZ DE SEEDING HISTÓRICO                        │
├─────────────────┬──────────┬───────────────────┬──────────────┬─────────┤
│ Periodo Corte   │ Moneda   │ Fecha Operación   │ TC Oficial   │ Estado  │
├─────────────────┼──────────┼───────────────────┼──────────────┼─────────┤
│ 2026-08-31      │ USD      │ 2026-09-10        │ 3.7500       │ pagado  │
│ 2026-08-31      │ PEN      │ 2026-09-10        │ 1.0000       │ pagado  │
│ 2026-06-30      │ USD      │ 2026-07-10        │ 3.7500       │ pagado  │
│ 2026-06-30      │ PEN      │ 2026-07-10        │ 1.0000       │ pagado  │
│ 2026-04-30      │ USD      │ 2026-05-10        │ 3.7500       │ pagado  │
│ 2026-04-30      │ PEN      │ 2026-05-10        │ 1.0000       │ pagado  │
│ 2026-02-28      │ USD      │ 2026-03-10        │ 3.7500       │ pagado  │
│ 2026-02-28      │ PEN      │ 2026-03-10        │ 1.0000       │ pagado  │
└─────────────────┴──────────┴───────────────────┴──────────────┴─────────┘
```

#### Reglas de Inmutabilidad durante el Seeding:
* **Prohibición de Tocar Saldos:** El script **ÚNICAMENTE** actualiza `payload_asiento`, `fecha_pago_real` y `estado_pago`. Queda estrictamente prohibido alterar montos de `capital_base`, `interes_generado_bruto`, `impuestos_renta`, `monto_reparto` o `capital_final_saldo`.
* **Estructura del Payload Inyectado:**
  ```json
  {
    "tipo_cambio": 3.7500,
    "fecha_operacion": "2026-07-10",
    "fecha_pago_real": "2026-07-10",
    "origen_seeding": "migracion_historica_oficial_2026",
    "ejecutado_el": "2026-09-11T..."
  }
  ```

## 📋 6. Hoja de Ruta y Checklist Pendiente para la Ejecución del Seeding (Siguiente Sesión)

Para cuando se reanude la sesión y el usuario haya completado las columnas del Excel, se seguirá este procedimiento canónico paso a paso:

### Fase 1: Recepción y Validación del Archivo Excel
- [ ] **Ubicación del Archivo:** [PLANTILLA_FECHAS_OPERACION_Y_TC_HISTORICOS.xlsx](file:///C:/Users/rguti/Inandes.ERP.React/Exceles.Ricardo.Gallo/PLANTILLA_FECHAS_OPERACION_Y_TC_HISTORICOS.xlsx).
- [ ] **Validaciones de Integridad Previas:**
  1. Verificar que ninguna de las 74 filas tenga valores nulos o vacíos en `FECHA OPERACIÓN / PAGO` o en `TIPO DE CAMBIO`.
  2. Validar que las fechas sigan estrictamente el formato ISO `YYYY-MM-DD` (ej. `2026-03-10`).
  3. Validar que los tipos de cambio sean números decimales positivos válidos (ej. `3.7500` para USD y `1.0000` para PEN).

### Fase 2: Construcción del Script de Migración (`scratch/execute_seeding_from_excel.py`)
- [ ] Construir el script en Python que:
  1. Cargue la matriz del Excel con `openpyxl`.
  2. Cree un diccionario de búsqueda indexado por `(id_fondo, fecha_periodo_fin)`.
  3. Ejecute primero una **Simulación (Dry-Run)**:
     - Imprimir cuántos eventos en `crm_certificados_eventos` se verán actualizados por cada corte.
     - Detectar si hay contratos huérfanos o fondos no mapeados.
  4. Ejecute el **UPDATE real en Supabase por bloques (chunks de 50)**:
     - Inyecta `payload_asiento = { "tipo_cambio": tc, "fecha_operacion": f_op, "fecha_pago_real": f_op, "origen_seeding": "migracion_historica_2026" }`.
     - Actualiza `fecha_pago_real = f_op` y `estado_pago = 'pagado'`.
     - **Regla Intangible:** Cero modificaciones a los campos numéricos de saldo, capital, retención o intereses.

### Fase 3: Pruebas de Control de Calidad (QC) y Verificación End-to-End
- [ ] **Auditoría en Supabase:** Verificar mediante script de consulta que 0 eventos históricos tengan `payload_asiento: null`.
- [ ] **Prueba End-to-End en Bot de WhatsApp:**
  - Enviar mensaje `"HOLA"` al bot con número de prueba.
  - Seleccionar **Opción 2 (Certificado de Retención)** $\rightarrow$ Submenú de periodos $\rightarrow$ Elegir corte histórico de `2026-06-30` o `2026-04-30`.
  - Verificar que el PDF despachado adjunte el TC oficial congelado y la Fecha de Operación registrada en el Excel.
