# Dictamen Forense: Caso de Rescates Pendientes vs Aplicados (Desincronizacion Ledger - Cronograma)

**Fecha:** 2026-09-08  
**Proyecto:** Inandes ERP (Modulo de Estado de Posicion Financiera)  
**Sistema:** React / Vite + Supabase PostgreSQL (`egvcinsbyropumybatdf`)  
**Metodologia:** Investigacion Forense Benoit Blanc (BEN-LEG-CLON-DIFF-QC-NOTA)

---

## 1. Descripcion del Hallazgo y Evidencia del Usuario

Durante la auditoria visual del reporte de **Estado de Posicion Financiera** (ejemplo: Contrato `NSGPEN01-001.20160101` de la inversionista *Parra Forero Gladys Yanneth*), se identifico una aparente contradiccion entre el **Ledger de Cortes Periodicos** y el **Cronograma de Deducciones / Rescates**:

1. **En el Ledger de Cortes (Tabla Superior):**
   - Al corte del **28/02/2026** (Asiento `#11756`), el motor financiero habia amortizado exitosamente un rescate de **S/ 325,000.00**, reduciendo el saldo del contrato de S/ 1,900,000.00 a S/ 1,575,000.00.
2. **En el Cronograma de Deducciones / Rescates (Tabla Inferior):**
   - La cuota `RES-NSGPEN01-001.20160101.260331.260228-C.1/1` correspondiente al 28/02/2026 figuraba con badge amarillo **`PENDIENTE`** y sin identificador de asiento contable (`Asiento: -`), a pesar de que los cortes posteriores (30/04/2026 y 30/06/2026) figuraban correctamente como **`APLICADO`**.
   - Las cuotas con fecha 31/08/2026 y 31/08/2028 figuraban como **`PENDIENTE`**, lo cual era correcto ya que dichos periodos aun no habian cerrado en el ledger.

---

## 2. Analisis Causa Raiz (Rastreo de Codigo Backend)

Al auditar la base de datos Supabase y el codigo fuente del backend Python en `mini_erp_v2_antigravity`, se identificaron tres factores determinantes:

### Causa 1: Desacoplamiento Transaccional entre Tablas
En la arquitectura de base de datos existen dos tablas independientes:
- `crm_certificados_eventos`: Contiene los asientos inmutables del ledger contable (cortes periodicos, capitalizaciones, amortizaciones).
- `crm_cronograma_deducciones_rescates`: Tabla satelite que almacena las proyecciones y solicitudes de retiro/deduccion.

No existia una foreign key estricta ni triggers en PostgreSQL que sincronizaran automaticamente el estado de la cuota cuando se registraba un evento de amortizacion en `crm_certificados_eventos`.

### Causa 2: Inserciones Masivas / Batch sin Actualizacion Satelite
En el modulo legacy (`modules/17_CRM_Inversionistas_v40.py`), el cierre de ciclo ejecuta tres pasos secuenciales:
1. `crm_certificados_eventos.insert()`
2. `crm_contratos.update()`
3. `crm_cronograma_deducciones_rescates.update({"estado": "PROCESADO"}).in_("id_cuota", ...)`

Cuando determinados periodos historicos (como febrero 2026) fueron recalculados o cargados mediante scripts independientes de rescate/ajuste batch (ej. `_insert_deducciones_feb.py`), se insertaron los asientos contables directamente en el ledger, pero **se omitio el paso 3** sobre la tabla satelite de cronogramas.

### Causa 3: Discrepancia de Nomenclatura y Efectos del Rollback
- El backend legacy guardaba el estado como `"PROCESADO"` al cerrar ciclo.
- La herramienta de Rollback (`Herramientas de Seguridad v40`) reseteaba masivamente las cuotas del periodo a `"PENDIENTE"`.
- Si se ejecutaba un Rollback y posteriormente los asientos se reinsertaban por otra via sin disparar el proceso de marcado de cuotas, el cronograma quedaba permanentemente estancado en `"PENDIENTE"`.

## 3. Acciones de Saneamiento y Correccion

### Paso A: Saneamiento de Datos en Supabase
Se ejecuto un script de auditoria y conciliacion (`sync_rescates_db.py`) que audito todas las cuotas de la tabla `crm_cronograma_deducciones_rescates`:
- **Resultado:** Se detectaron y sanearon **27 cuotas historicas** que tenian eventos amortizados en el ledger pero estaban marcadas como `PENDIENTE`.
- **Accion aplicada:** Se actualizo su estado a **`APLICADO`** y se vinculo su respectivo **`id_evento_ledger`**.

### Paso B: Conciliacion Dinamica en el Servicio Frontend (`estadoPosicionService.ts`)
Para garantizar que nunca mas ocurra una discrepancia visual (incluso si la base de datos tuviera cuotas desincronizadas a futuro), se integro un algoritmo de conciliacion automatica en memoria:

```typescript
// src/services/estadoPosicionService.ts
const rescatesByContract = new Map<string, RescatePositionItem[]>();
allRescates.forEach(r => {
  if (!rescatesByContract.has(r.id_contrato)) {
    rescatesByContract.set(r.id_contrato, []);
  }
  const fechaProg = r.fecha_proyectada_cobro ? String(r.fecha_proyectada_cobro).split('T')[0] : '';
  const contractEvents = eventsByContract.get(r.id_contrato) || [];

  // Buscar si existe un evento en el ledger que ya amortizo este rescate
  let matchingEvent = r.id_evento_ledger
    ? contractEvents.find(e => e.id_evento === r.id_evento_ledger)
    : null;

  if (!matchingEvent && fechaProg) {
    matchingEvent = contractEvents.find(e => e.fecha_periodo_fin === fechaProg && e.amortizacion_rescate_monto > 0);
  }

  const isAplicado = Boolean(matchingEvent) || r.estado === 'APLICADO';
  const estadoFinal = isAplicado ? 'APLICADO' : (r.estado || 'PENDIENTE');
  const idEvtAplicado = matchingEvent ? matchingEvent.id_evento : (r.id_evento_ledger || null);

  rescatesByContract.get(r.id_contrato)!.push({
    id_cuota: r.id_cuota,
    id_contrato: r.id_contrato,
    id_inversionista: r.id_agrupador || '',
    tipo: r.tipo_cargo || 'RESCATE_CAPITAL',
    descripcion: r.glosa_descripcion || '',
    moneda: r.moneda || 'USD',
    monto: Number(r.monto_cobrar || r.monto || 0),
    fecha_programada: fechaProg,
    estado: estadoFinal,
    id_evento_aplicado: idEvtAplicado,
    fecha_pago_real: null
  });
});
```

### Script 1: Auditoria Integral al 100% de Cuotas y Eventos (`audit_all_deductions.py`)
Permite escanear la totalidad de cuotas en `crm_cronograma_deducciones_rescates` y cruzarlas con los asientos del ledger en `crm_certificados_eventos`:

```python
import os
import json
from collections import Counter
from supabase import create_client

url = "https://egvcinsbyropumybatdf.supabase.co"
key = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." # Credencial Supabase del proyecto

# 1. Obtener todas las filas de crm_cronograma_deducciones_rescates

# Contar por tipo_cargo y estado

for c in all_cuotas:
    tipo = c.get('tipo_cargo') or 'SIN_TIPO'
    estado = c.get('estado') or 'SIN_ESTADO'
    by_type_and_status[(tipo, estado)] += 1

for (t, e), count in sorted(by_type_and_status.items()):
    print(f"Tipo: {t:<25} | Estado: {e:<15} | Cantidad: {count}")

# 2. Obtener todos los eventos para cruzar deducciones y rescates

print(f"\nTotal eventos en crm_certificados_eventos: {len(all_evts)}")

# 3. Analizar cuotas PENDIENTES
print("\n--- DETALLE DE TODAS LAS CUOTAS PENDIENTES ---")
pendientes = [c for c in all_cuotas if c.get('estado') == 'PENDIENTE']
for p in sorted(pendientes, key=lambda x: str(x.get('fecha_proyectada_cobro'))):
    f_cobro = str(p.get('fecha_proyectada_cobro') or '').split('T')[0]
    cid = p.get('id_contrato') or p.get('id_certificado')
    tipo = p.get('tipo_cargo')
    monto = p.get('monto_cobrar') or p.get('monto')
    
    # Buscar si hay evento en esa fecha
    ev_same_date = [e for e in all_evts if e.get('id_contrato') == cid and str(e.get('fecha_periodo_fin') or '').split('T')[0] == f_cobro]
    
    status_match = "SIN_EVENTO_EN_FECHA (FUTURO O NO CERRADO)"
    if ev_same_date:
        ev0 = ev_same_date[0]
        payload = ev0.get('payload_asiento') or {}
        if isinstance(payload, str):
            try: payload = json.loads(payload)
            except: payload = {}
        
        deds_in_payload = payload.get('detalle_deducciones', [])
        rescs_in_payload = payload.get('detalle_rescates', [])
        status_match = f"EVENTO_EXISTE (IdEvt: {ev0.get('id_evento')}, RescateEvt: {ev0.get('monto_rescate')}, DedsPayload: {len(deds_in_payload)}, RescsPayload: {len(rescs_in_payload)})"
        
    print(f"Contrato: {cid:<26} | Tipo: {tipo:<20} | Fecha: {f_cobro:<10} | Monto: {monto:>10} | {status_match}")
```

### Script 2: Saneamiento y Enlace Masivo de Rescates de Capital (`sync_rescates_db.py`)
Actualiza el estado a `APLICADO` y enlaza el `#id_evento_ledger` para las 27 cuotas de rescate amortizadas en el ledger:

```python
import os
from supabase import create_client

url = "https://egvcinsbyropumybatdf.supabase.co"
key = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." # Credencial Supabase del proyecto
sb = create_client(url, key)

rescs = sb.table('crm_cronograma_deducciones_rescates').select('*').execute()
print(f"Total cuotas a analizar: {len(rescs.data)}")

updated_count = 0
for r in rescs.data:
    ct = r.get('id_contrato')
    f = str(r.get('fecha_proyectada_cobro') or '').split('T')[0]
    if not ct or not f:
        continue
        
    ev = sb.table('crm_certificados_eventos').select('*').eq('id_contrato', ct).eq('fecha_periodo_fin', f).execute()
    matching_evs = [e for e in ev.data if float(e.get('monto_rescate') or 0) > 0]
    
    if matching_evs:
        matched = matching_evs[0]
        if r.get('estado') != 'APLICADO' or not r.get('id_evento_ledger'):
            sb.table('crm_cronograma_deducciones_rescates').update({
                'estado': 'APLICADO',
                'id_evento_ledger': matched.get('id_evento')
            }).eq('id_cuota', r.get('id_cuota')).execute()
            print(f"ACTUALIZADO: {r.get('id_cuota')} -> APLICADO con IdEvento: {matched.get('id_evento')}")
            updated_count += 1

print(f"\nTotal cuotas actualizadas en BD: {updated_count}")
```
